# 迭代记录

本文对应项目的“迭代 md”，记录需求、实施、验证和剩余工作。功能差异见 [修改记录](CHANGELOG.md)，完整数据与验收矩阵见 [测试报告](TEST_REPORT.md)，本轮实施顺序见 [PLAN.md](../PLAN.md)。

## 迭代一：从需求文档建立工程

时间：2026-10-26。依据根目录安卓需求文档创建离线图片转 PDF 工程，采用 Kotlin、Compose、最低 API 26、单任务最多 500 张、每图一页、先生成私有完整结果再另存的方案。

核心实现包括受控 URI 导入、采样解码、EXIF 八方向与用户旋转、串行 JPEG 编码及流式 PDF 写入、后台通知与取消、原子草稿状态、SAF 导出、受限分享 URI 和按需预览。转换开始后冻结顺序与设置，进程中断后从头重试。

先取得 19 项 JVM 测试，以及 100 / 300 / 500 页带编号 JPEG 的宿主 PDF 独立解析和渲染结果。宿主样本为 900×1200 合成图片，这些结果只证明布局、结构和写入器正确性，没有被当作安卓 12MP 性能数据。

## 迭代二：1.0.1 单批 500 张与测试隔离

时间：2026-10-26。用户明确要求单次可提交 500 张以内图片，批量主入口采用系统文件多选，Photo Picker 作为辅助入口。应用消费一次 500 URI 响应，并为 501 项提供显式确认与取消路径。

追加导入保留原列表，原始 URI 用于跨私有副本的重复提示；修复后台任务结束竞态、源清理并发、空间不足持久化错误和选择器异常。测试构建使用独立 `.benchmark` 包名，避免测试覆盖用户主应用数据。

设备验证经历了安装器本次授权和测试初始化返回类型修复。最终隔离功能套件六项通过，覆盖图片管线、真实前台服务生成、顺序 / 配置冻结、Activity 重建、取消另存、受控私有目标导出哈希和新建后结果保留。另一次单批 500 / 501 URI 导入回归通过。此前 AppFlow 因已有草稿而跳过的一轮按“4 通过、1 跳过”记录，没有省略跳过状态。

## 迭代三：1.0.2 真正的应用内“全选”

时间：2026-10-27。仅依赖系统多选不能稳定提供用户想要的全选体验，因此增加目录授权后的应用内 FolderPicker：顶部固定全选 / 取消全选，底部一次导入，额度和超额确认清晰可见。只枚举当前目录，保持自然排序及同名稳定顺序。

生产主应用 1.0.2 已完成覆盖安装并由设备版本信息确认。为验证控件，测试临时挂载真实生产 FolderPicker，以独立 ImageRepository 导入合成图片，同时断言原运行时图片与结果保持相等。

测试修复与实际结果按轮次保留：

| 轮次 | 实际结果 | 处理与界限 |
| --- | --- | --- |
| Kotlin 独立夹具 | 3 失败、1 跳过 | 独立 receiver 进程缺少 Kotlin Intrinsics；UI 用例保护已有草稿而跳过，不能算通过 |
| Java 广播授权 | 4 失败 | 授权回执为 0 / null，不能归因为生产目录枚举错误 |
| 同步 ContentProvider 桥 | 4 失败 | 报 Unknown authority，但现场确认名称和注册存在，未把候选原因写成定论 |
| 仅 benchmark 包可见性配置 | 4 失败 | 该轮没有解决桥访问，生产主应用权限未改变 |
| 四个合成根临时预授权 | 3 通过、1 失败 | 元信息用例通过，UI 因 UiAutomation Binder 死亡失败 |
| 设备端持久 runner | 3 通过、1 失败 | UI 首次点击前等待超时，没有当作已点击成功 |
| BFS 控件查找最终轮 | **4 通过，无失败或跳过** | 实际点击“全选”和“导入已选 500 张”，500 项有效、ID 唯一、顺序正确，原运行时状态保护断言通过 |

最终轮使用四个受控合成根的非持久 prefix 读取预授权、设备端持久 runner，以及普通 MAIN / LAUNCHER 前台辅助。没有操作用户目录或更改系统电源 / 安全设置；控件查找严格限制本测试应用。

最终套件耗时 **4.488 秒**，图片由微小 PNG 夹具提供。它验证选择控件与独立导入管线，不是 500 张 12MP 转换耗时，也不等于个人目录的系统选择 / 授权或普通应用首次跨 provider 自动授权已经验证。

## 迭代四：500 张合成 12MP 真机长测

首次 1.0.1 压力尝试完成 100 / 300 张，500 张在第 326 页记录后遭系统一键清理强停；证据显示 USER REQUESTED / FORCE STOP / single-cleaner，没有 Java OOM 证据。原始目录、中断临时文件及未完成重试日志都保留。

最终 1.0.2 在 vivo V2505A（约 16 GB RAM、应用堆 256 MiB）上以固定 4000×3000 合成 JPEG 连续转换三轮：

| 轮次 | 转换耗时 | 输出 | 五分钟目标 |
| --- | --- | --- | --- |
| 1 | 319.554 秒 | 500 页，153,891,616 bytes | 未通过 |
| 2 | 208.408 秒 | 500 页，153,891,616 bytes | 本轮低于五分钟 |
| 3 | 130.215 秒 | 500 页，153,891,616 bytes | 本轮低于五分钟 |

每轮 500 行原始采样和外部 1,066 份内存快照保留。测试期间观察到冻结与 CPU 停顿，并用普通前台 Intent 辅助；没有精确扣除冻结时间，也不把首轮超标全部归因于冻结。源样本生成和完成后的证据镜像复制不计入每轮转换耗时。

三轮都有 Android 页数与首中末断言；最终留存 PDF 完成独立严格解析、500 页顺序条码和横向 A4 检查，哈希与已校验文件一致。前两轮与最终全文独立校验的范围分别记录，没有扩写为所有输出都逐页复核。

结论是“完成这台设备上、注明条件的三轮合成样本转换”，不是完整 V1 认证。真实相机与混合格式、4 GB 设备、真实系统目录 / SAF、熄屏后台、取消最坏时延及连续真实峰值仍需补齐。
